# qwen3:4b 与 gemma4:12b 同题对照报告

日期：2026-10-22。分支 `eval/gemma4-12b-comparison`。两套已见回归题集（generalization_v1、holdout_v2，各 40 题），以及 S5 售后服务 test 集的端到端任务（30 题，react 与 plan 两种模式）；同一台机器、同一代码、同一检索索引，只替换聊天模型。环境、token 计数修复与运行方法见 [对照说明](../artifacts/gemma4_comparison/README.md)。

## 结论

**在答案质量上，gemma4:12b 好于 qwen3:4b，差距集中在知识问答的忠实度；Agent 任务两者持平。**

- 知识题严格通过：qwen3:4b **40/56**，gemma4:12b **48/56**。配对看，只有 gemma 通过 10 题、只有 qwen 通过 2 题。
- 差距主要不是“答错”，而是 qwen 更常加入本次资料不支持的内容，或把相邻条目的做法套到所问问题上：知识与资料不足题中，qwen 有 10 个回答忠实度不通过，gemma 有 2 个；内容不完整（分数低于 2）两者相近，qwen 9 个、gemma 7 个。
- 资料不足题：qwen 11/12，gemma 12/12，两者都没有编造所问数值。
- Agent 全轮任务：两者都是 11/12，失败的是同一题（G1A05）。本项目的报表查询与知识引用多由程序确定性生成，Agent 层几乎不区分两个模型。
- 速度：单次知识问答 gemma 较慢（中位数 2.3–3.2 秒，对 1.5–1.6 秒）；Agent 每轮 gemma 反而较快（中位数 13–18 秒，对 17–23 秒），尾部时延也更小。
- 端到端售后任务（S5 test 30 题）：全轮任务通过 qwen3:4b react **10/30**、plan **9/30**；gemma4:12b react **14/30**、plan **14/30**。两种模式下配对都是 gemma 独有通过 5 题，qwen 独有通过分别为 1 题和 0 题；六项硬门槛事件四次运行均为 0。详见[端到端售后任务](#端到端售后任务s5-test-集)。

## Agent 层为何持平

24 个 Agent 案例中，报表查询的最终回答由确定性渲染生成，维护条目常走生产校验的原文引用，两模型输出大多逐字相同；差别只在检索词改写与是否多调用 `get_user_id` 等，不影响结果。模型真正起作用的是长历史回忆轮与少数 RAG 总结轮，两者表现一致，G1A05 第二轮都没能遵守回忆出的“分章节说明”要求。

知识层同理有 7 题（G1K03、G1K06、G1K07、G1N05、V2K03、V2K19、V2N03）走程序校验引用或固定拒答，没有调用模型，两者逐字相同且都通过。

### 两个模型的错法

- **qwen3:4b**：卡片生成积极（react 召回 16/20），但多次在确认前写成已完成——“已为您改约至1月22日”（T10）、“已为您取消边刷耗材订单”（T23 撤回轮）、“您的订单已生成”（T07）；另有无据补充（“工程师将尽快联系您”、“已触发更换提醒”、检查水位/提供照片）和“回复确认即可下单”这类与卡片确认机制不符的说明（T20）。plan 下有一题只查订单和预约就回答“没有查到相关记录”，漏掉存在的工单（T15）。
- **gemma4:12b react**：不愿生成卡片——20 张应有卡片只出了 8 张，有时在文字里说“确认后我将为您提交订单”却没有调用提议工具（T06），或提议参数未通过策略校验（T03）。不需要卡片的题全部做对，复核中没有出现“确认前称已完成”。
- **gemma4:12b plan**：规划后能把卡片生成出来（T01–T06 自动判分全部通过），四次运行中唯一没有预算超限或截断的一次。语义失败集中在两类：漏答必需信息（申请准备漏型号/购买日期/凭证、超限购没明说不能买、只查当天时段）；以及回答里附带的资料说明写“无法确认在保/无法确认时段可约”，与同一回答中系统查得并已生成卡片的事实矛盾（T01、T02、T04、T16）。另有一题开头误称“指定时段没有名额、未生成卡片”而卡片实际已生成（T03）。

**口径敏感性**：资料说明来自 RAG 子调用，plan 模式常把整句用户问题交给 RAG，RAG 在只看文档时说“无法确认”保修或时段。本评审把这类与系统事实矛盾的结论记为内容缺陷。若改为只看模型主体回答、不计资料说明中的“无法确认”，gemma4 plan 为 16/30（T02、T04 转为通过；T01 仍缺电池保修，T16 仍缺申请准备项）、react 为 15/30（T19），qwen3 两种模式不变。

### 解读限制

- 只对自动判分通过的任务做语义复核（75 个用户轮），自动失败的任务不可能通过，记为未复核失败；因此“复核用户轮”的分母在各运行间不同。
- 复核由 Claude 助手完成，四次运行的样本混合、隐藏运行标签后评分并锁定再揭盲；但评审前已看过各运行的自动通过分布，只在一次运行中自动通过的题可由题面推断来源，盲评不完整。
- 每种组合只运行一次，30 题小样本，不作显著性结论；S5 成绩来自旧代码与旧机器，不作直接比较。
- `evaluation/service_review.py` 为此增加了 `--automatic-pass-only` 选项（默认行为不变），本次四个运行目录记录的评测代码哈希是修改前的版本。

## 评审方法

以下为两套问答题集的评审方法；端到端售后任务的复核方式见上节。

- 每题按各题集冻结的 SCORING.md 判内容分（0/1/2）与忠实度。忠实度只认该次实际送入模型的证据、有效工具结果和会话历史。
- 两模型答案按题配对、以 X/Y 呈现，顺序按固定种子随机；对照键存放在仓库外，评分写入 `blind_scores.jsonl` 并记录 SHA256 锁后才揭盲。揭盲后评分逐条绑定结果 `result_sha256`，再由 `evaluation.report` 汇总。
- 忠实度判得较严：加入本次输入没有的理由或数值、把其他条目的处理套用到所问情形、丢掉数值的适用前提，都记为不忠实，即使内容本身听起来合理。这一口径对两模型一致，但会放大“回答更长、补充更多”的一方的失败数。

## 限制

- **评审者不独立**：评分由 Claude 助手完成。同一助手搭建了本次环境与计数器，并在冒烟测试中见过 3 题输出；两模型回答风格不同（gemma 更简短、qwen 更常附加说明），标签隐藏不能完全防止识别。这不是独立真人或领域专家盲评。
- **已见题**：两套题此前都用于修复，属于已见回归，不代表未见泛化能力。
- **单次运行**：每个模型每套题只跑一次，temperature 0，未测量重复波动。
- **上下文窗口**：两模型同为 8192 token；同一文本 gemma 约多用 7% token，未做补偿。
- **历史对照**：仓库中 qwen3:4b 在较早代码上由另一评审团队给出的成绩为 generalization 20/28、6/6、4/6，holdout 22/28、6/6、6/6；本次 qwen 重跑为 19/28、6/6、5/6 与 21/28、5/6、6/6，量级一致。两者代码与评审者不同，不作直接比较。
